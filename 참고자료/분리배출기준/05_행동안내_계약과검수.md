# 단계별 행동 안내의 계약과 검수

적용 범위: 기존 상세/단계별 소비자의 기준과 검수 이력이다. 현재 기본 화면은 통화형이며 생성 발화의 검증 경계가 다르다. [현재 아키텍처](../../docs/architecture.md)를 먼저 확인한다. 아래 조사·조건·당시 검증 기록은 보존한다.

확인일: 2026-10-08. 이번 범위는 송파구 가정용 음료·식품 금속캔, 플라스틱 세정용 펌프 용기, 투명 생수·음료 PET병이다. 상품명이 달라도 재질·용도·부품이 적용 조건에 맞으면 안내하며, 새 이름만으로 거절하지 않는다. 기존 상세 API의 10종 ID와 규칙 선택은 유지한다.

## 행동과 근거의 연결

- `src/data/disposal-rules.ts`가 공식 규칙과 출처의 단일 원본이다. `coach-guides.ts`는 기존 `RULES`의 조건·출처를 투영한다. 새 금속캔 규칙도 원본에 추가하며 기존 `ItemId`에는 새 값을 끼워 넣지 않는다.
- 모든 단계의 `reason`은 지금 행동의 이유, `ruleIds`는 적용 조건, `sourceIds`는 기관·절·원문·확인일을 연결한다. URL 목록만으로 조건이 충족됐다고 보지 않는다.
- 펌프 구조·재질·비움·세척은 사용자 답이 필요하다. 흐름의 `facts.evidence`는 이 경계를 선언하고 모델 관찰에는 이 사실, 배출 분류, 규칙 ID, 완료 사실을 허용하지 않는다.
- 일반 금속캔은 알루미늄 음료캔 또는 철 식품캔을 확인하고, 다른 재질 부품이 없으며, 비움·이물질 제거를 직접 보고한 경우에만 금속캔 분류에 도달한다. 다른 재질 덮개는 검수하지 않은 분류를 만들지 않고 보류한다.
- 분리할 수 없는 펌프·라벨에는 검수된 대안이 없어 보류한다. PET 압착만 원문의 가능한 범위를 적용하므로 안 눌리면 추가 힘을 요구하지 않고 뚜껑 단계로 진행한다. 찌르기·가열·강제 분해를 지시하지 않는다.
- 부품 분류는 각 부품의 준비 단계 이후에 나타난다. 나중에 다른 부품이 보류되면 전체 완료로 표시하지 않는다. 같은 이력에서 이미 준비한 부품의 분류는 유지하고, 아직 해결하지 못한 부품만 보류한다. 완료는 사용자 준비 완료 보고이고 AI 인증이 아니다.
- 식품용 EPS의 기존 송파구 자료 충돌, 성분을 모르는 아이스팩, 배터리·전자제품·대형·위험물은 일반 포장재 정답으로 채우지 않는다. 복구 흐름은 확인되지 않은 사유와 표시·사진·용도 및 송파구 공식 담당 경로를 안내한다.

## 계약과 검증 경계

`src/lib/contracts/coach.ts`는 zod strict 스키마를 제공한다. 객체·세션·사진·요청 UUID, 음성/진행 상태, 좌표, 카탈로그 참조, 사진 참조, 물건과 흐름의 일대일 관계, 단계 내 선택, 조용한 순환, 조건·출처, 도움 답의 현재 단계 연결을 검사한다.

최종 물건·부품 ID는 서버가 부여한다. 모델 후보 스키마에는 해당 ID가 없다. 사진 모드는 현재 사진의 실제 view가 필요하고 직접 입력은 view가 비어야 한다. 이력은 시작 단계부터 재생하며 앞 단계 수정은 그 이후 이력을 잘라 사실까지 버린다. 도움 답은 카탈로그의 문장·선택 ID만 반환한다. 음성 재생 종료를 단계 선택으로 처리하지 않는다.

사진 해독·multipart의 파일 개수 및 MIME·크기, WAV 단일채널 24kHz/16bit·20초·1MiB, 서비스 호출·no-store·응답 취소는 API/클라이언트 통합에서 별도로 검증한다. 계약 모듈의 정수·배열 상한만으로 실제 파일 해독을 검증했다고 주장하지 않는다.

T1 실행 기록: 새 계약 테스트를 먼저 실행해 모듈 없음으로 RED(exit 1)를 확인했다. 구현 뒤 새 계약 및 기존 규칙 테스트를 실행해 94개 GREEN(exit 0)을 확인했다. 타입 검사에서 초기 단계 변수의 타입 좁히기 오류를 발견해 수정했다. 최종 `npx vitest run tests/contracts/coach.test.ts tests/rules`, `npm run typecheck`, 변경한 TypeScript 5개 파일의 `npx eslint`는 모두 종료코드 0이었다. `git diff --check`도 통과했다. 모델 실호출·물리 기기·현장 정확도·메인 빌드는 이 자료 단계의 검증 범위가 아니다.

## 독립 검토 후 계약 보완

- 펌프·라벨·뚜껑이 없다고 답한 뒤 다른 행동에 실패했을 때 공통 보류 단계가 없는 부품까지 다시 표시하는 결함을 재현했다. 부품 존재 사실은 같은 역할명 키(`pump`, `label`, `cap`)의 `none` 또는 `absent`로 선언한다. 이 사용자 답을 기준으로 현재 단계의 대상·배출 목록 및 누적 배출 목록에서 없는 부품을 제외한다. 카탈로그 원본은 수정하지 않는다.
- `CoachHelpRequestSchema`는 해독된 `context`, `choices`와 `text` 또는 `audio: Blob` 중 정확히 하나를 받는다. 글은 빈 값과 1,000자 초과, 음성은 빈 파일과 1MiB 초과를 거절한다. `validateCoachHelpRequest`는 이력을 재생해 현재 단계도 대조한다. WAV의 실제 형식·재생 시간 검사는 서버 파일 해독의 책임이다.
- `validateCoachHelpResponse(catalog, response, request)`는 글 요청의 `transcript: null`을 강제한다. 음성 성공 응답은 공백뿐이지 않은 1,000자 이내 전사를 요구한다. 무음·미해석 음성을 정상 전사로 꾸미지 않는다.
- `validateCoachSpeechRequest(catalog, request)`는 현재 단계 ID 또는 현재 단계에 허용된 도움 답 ID만 받아 검수된 `speechText`를 반환한다. 다른 단계·알 수 없는 ID·자유 text·유효하지 않은 이력을 거절한다. 합성기는 반환된 문장만 사용한다.

보완 검사에서 먼저 7개 실패(없던 부품 2개, 도움/음성 계약 5개), 종료코드 1을 확인했다. 구현 후 새 도움 계약·기존 계약·전체 규칙 102개는 종료코드 0이었다. `npm run typecheck`, 변경한 TypeScript 3개 파일의 `npx eslint`, `git diff --check`도 종료코드 0을 확인했다.

## 질문 의미에 따른 검수 답 보완

카탈로그 버전을 `songpa-coach-2026-10-08-v2`로 올렸다. 각 단계의 기존 `-help` ID를 유지하면서 행동 방법, 행동 실패, 이유, 현재 범위를 벗어난 질문을 다른 답으로 구분했다. 단계마다 무조건 같은 네 문장을 복제하지 않고 행동 실패 답은 실제 행동 단계에만 두며 범위 안내는 해당 흐름의 단계들이 공유한다.

- `pump-detach-cannot`: 펌프가 안 빠지면 힘을 더 주지 않고 멈추도록 안내한다. 확인된 다른 분리 방법이 없어 `cannot` 선택만 제안한다.
- `pet-flatten-cap-cannot` / `pet-flatten-open-cannot`: 기존 송파구의 가능한 압착 조건에 따라 강한 힘을 요구하지 않는다. `cannot`을 직접 선택하면 각각 뚜껑 닫기 또는 배출 준비 확인으로 갈 수 있음을 설명한다.
- `-why` 및 흐름별 `-scope-help`: 관련 이유·범위를 설명하되 선택 ID는 비워 둔다. 질문 발화만으로 사실을 적용하거나 진행하지 않는다.
- 펌프 스프링 미확인, 가스·스프레이 캔, 없는 PET 뚜껑에는 각각 `unknown`, `gas`, `absent`만 연결된 짧은 답을 둔다. 기존 조건·선택 분기·공식 배출 규칙은 변경하지 않는다.

음성은 이유와 긴 단계 본문을 이어 읽지 않고 짧은 문장을 따로 사용한다. 현재 모든 단계·답의 `speechText`가 80자 이하인 편집 검사를 통과했다. 이는 20초 이내의 짧은 안내를 위한 제약이며 실제 음성 재생 시간을 측정한 결과는 아니다. 실제 모델이 질문 의미에 맞는 답을 선택하는지와 합성 음성 길이는 T5 통합 검증에서 별도로 확인한다.

새 회귀 검사 7개를 먼저 실행해 종료코드 1을 확인한 뒤 구현했다. 규칙·계약·컨트롤러·카탈로그 통합 150개 검사, `npm run typecheck`, 변경 코드·테스트의 ESLint, `git diff --check`가 모두 종료코드 0이었다. 새 공식 처분 규칙이나 출처 확인일은 추가하지 않았다.


## 부품별 부분 준비 결과 보존

펌프 분리와 일반쓰레기 준비를 직접 확인한 뒤 라벨 문제로 보류하면, 펌프의 앞선 결과가 전체 보류에 덮이는 결함을 재현했다. 이력 재생은 같은 역할의 앞선 확정 분류를 뒤의 포괄 보류로 덮지 않는다. 없는 부품은 계속 제외하며, 아직 해결하지 못한 본체·라벨 등은 보류로 남는다. 준비된 부품이 있어도 보류가 하나라도 있으면 전체 완료가 아니다.

현재 단계의 `step.destinations`는 지금 보류할 부품만 담고, `destinations`는 이력에서 준비한 부품과 보류 부품을 각각 담는다. 중간 보류 화면도 후자의 누적 결과를 사용해야 한다. 결과를 별도 저장하지 않으므로 뒤로가기·이전 답 수정으로 분리 또는 준비 확인 이력이 없어지면 그 분류도 함께 사라진다.

펌프·PET 라벨의 부분 준비, 보류 전후 결과, 없는 부품 제외, 이전 답 수정, 컨트롤러와 서버 이력 재생 일치 검사를 추가했다. 먼저 5개 실패로 종료코드 1을 확인한 뒤 관련 규칙·계약·컨트롤러·도움 API·통합 180개 검사, 타입 검사, 변경 파일 ESLint, diff 검사를 종료코드 0으로 확인했다. 공식 기준·카탈로그 분기·컨트롤러·UI는 이 수정에서 변경하지 않았다.

# 구현 중 확인한 동작

## 2026-10-01 빠른 안내에서 확인한 조건과 관찰의 차이

예전 화면은 숨은 조건을 하나씩 확인하느라 질문·선택·재전송이 반복됐다. 기본 화면을 품목 인식과 배출 준비 안내로 나눴다. 카탈로그의 적용 조건은 관찰 사실이 아니므로 ‘깨끗함이 확인됐다’고 표시하지 않는다. 아이스팩과 EPS에는 기본 성분·용도를 자동 선택하지 않는다. 품목·상태 전환은 로컬이며 새로운 사진 요청과 경쟁하지 않도록 선택 순간 이전 요청을 취소하고 버전을 올린다.

## 기존 상세 API의 자유글에서 이전 답이 살아나는 경우

“다 비웠나요?” 같은 질문이나 “아까 답은 틀렸고 라벨은 있어요” 같은 정정을 단순 키워드로 읽으면 오래된 비움 사실과 새 라벨 사실이 함께 남을 수 있다. 발화가 정확히 존재한다는 검사만으로 의미가 확인되지는 않는다. 질문·인용·지시를 먼저 거르고, 등록 선택지나 제한된 명확한 자유글을 절 전체와 대조한다. 발화의 모든 절을 확인할 수 있을 때만 사실을 적용하며, 미해석 절이 하나라도 있으면 이전 확인값도 버리고 다시 묻는다. 따라서 자연스러운 표현이어도 등록된 의미를 확정하지 못하면 질문이 반복될 수 있다. 등록 선택지의 정상 부정문, 여러 조건을 담은 명확한 문장, 순차 단일 답은 유지한다. 정정 이후 앞선 사용자 근거가 재주입되지 않도록 사실별 최신 발화 위치도 확인한다. 변경 시 혼합 정정·문구 작성 요청·이전 근거 재사용과 정상 답을 함께 회귀 검사한다.

## 상품사진은 내부 상태의 정답지가 아니다

공개 상품사진은 물체 형상을 준비하기 쉽지만 내용물·청결·실제 성분을 증명하지 않는다. 특히 시험에 사용한 EPS 상자 사진은 식품 포장 판매사진인데 비식품 배송이라는 가상 답을 주었다. 이는 조건 전달 시험이며 식품용 EPS의 처리 정답 근거가 아니다. 사진의 용도나 보이는 부품과 사용자 답이 충돌하는 경우를 따로 시험해야 한다. 음료팩의 보이는 빨대를 ‘없음’이라고 답한 사례에서는 재확인이 필요했다.

## 큰 사진의 파일 크기와 해상도는 다르다

단색 4,800만 화소 JPEG는 파일 크기가 작아도 서버 해독 한도를 넘는다. 브라우저에서 파일 바이트 검사만 하면 선택은 성공하고 분석 때 뒤늦게 실패한다. 전체 비율을 유지한 크기 축소가 필요하며, 잘라내기로 제품 표시를 잃지 않게 한다. 실제 파일 입력에 8,000×6,000 이미지를 넣고 4,096×3,072 미리보기로 바뀌는 것을 확인했다. 인공 단색 사진이므로 품목 인식 시험에는 사용하지 않았다.

## 타입 검사와 격리 디렉터리

처음 설치한 디렉터리는 Next.js 생성 경로 타입이 없을 수 있다. `tsc`만 실행하면 실제 코드 결함과 생성물 누락이 섞이므로 `npm run typecheck`가 먼저 `next typegen`을 실행한다. 생성된 `next-env.d.ts`와 빌드 결과를 소스처럼 편집하지 않는다.

Turbopack은 프로젝트 밖을 가리키는 `node_modules` 심볼릭 링크를 거절할 수 있다. 별도 디렉터리에서 실행해야 하면 그 위치에 `npm ci`로 의존성을 설치한다. 타입 검사만 성공했다는 이유로 링크된 디렉터리의 서버 실행도 성공했다고 판단하지 않는다. 실제 build 또는 dev 시작과 HTTP 응답으로 확인한다.

## 화면 크기 검증의 한계

현재 Aside 환경에는 viewport 변경 메서드가 없었다. QA 전용 iframe의 CSS viewport를 바꾸고 문서의 `clientWidth`·`scrollWidth` 및 캡처를 함께 확인했다. 일반 데스크톱 스크롤바 때문에 390px frame의 clientWidth는 375px이었다. 이 차이는 가로 넘침을 뜻하지 않는다. iframe 방식은 앱 기능이 아니며 모바일 사용자 에이전트·가상 키보드·실물 카메라를 재현하지 않는다.

Aside 파일 입력은 숨겨진 input이 포함된 새 스냅샷을 얻은 뒤 경로 배열로 지정한다. 이후 스냅샷에서 숨겨진 노드가 빠졌으면 이전 ref를 재사용하지 않는다. 결과의 긴 출처 목록이 옆 사진 카드 높이까지 늘어나는 문제는 열 정렬에서 발생했다. 결과·출처를 펼친 태블릿 화면까지 확인해야 초기 화면 검사에서 놓치지 않는다.

## 이미 취소된 요청의 Promise 정리

HTTP 오류를 반환했어도 Node에 미처리 rejection이 남을 수 있다. 이미 작업 Promise가 시작된 뒤 취소 검사에서 바로 throw하면 그 작업의 실패를 소비할 핸들러가 붙지 않기 때문이다. 취소된 signal에서도 작업과 취소 Promise 양쪽에 핸들러가 붙도록 경쟁 처리를 구성한다. 미리 취소한 요청으로 HTTP 오류·모델 호출 0회뿐 아니라 미처리 rejection 0건과 처리 슬롯 회복까지 확인한다.

## 음소거가 도움 답을 지우는 경우

펌프 분리 도움 답을 받은 뒤 소리를 끄면 화면의 답까지 사라지는 문제가 있었다. 안내 경로를 바꾸는 초기화와 오디오만 중단하는 수명을 분리해 도움 답·입력은 유지하도록 수정했다. 검증할 때 ‘질문 응답 → 음소거 → 답·제안 선택지 유지’를 확인하고, 물건 전환처럼 실제 맥락이 바뀔 때는 이전 답이 제거되는지도 함께 확인한다.

## 보류 화면에서 이미 준비한 부품이 사라지는 경우

펌프를 준비한 뒤 라벨을 보류하거나, 일반 용기의 뚜껑을 준비한 뒤 필름이 안 떨어지면 포괄 보류 단계가 앞선 부품 결과까지 덮는 문제가 있었다. 선택 이력에서 부품별 목적지를 합치며 이미 준비한 부품과 아직 보류한 부품을 구분한다. 현재 단계의 목적지만 표시하면 또 누락되므로 부분 결과에서는 누적 결과와 각 부품의 해당 단계 근거를 함께 확인한다. 이전 선택을 정정하면 이 누적 결과도 남은 유효 이력에서 다시 계산해야 한다.

## LAN 주소의 개발 화면이 준비 중에서 멈추는 경우

localhost는 열리는데 LAN 주소에서는 준비 중에 머무는 현상과 Next 개발 서버의 HMR 출처 차단을 함께 확인했다. 현재 장치의 정확한 RFC1918 IPv4만 allowedDevOrigins에 넣고 서버를 재시작한 뒤 같은 LAN HTTP 주소에서 화면과 수동 안내를 확인했다. 주소가 바뀌면 출처 목록도 다시 읽어야 한다. 이 HTTP 화면 성공은 마이크의 보안 연결 조건을 충족하지 않는다.

## 음성 텍스트 일치와 실제 듣기 품질은 별개

검수 문장과 Realtime 출력 텍스트 대조를 통과한 WAV에서 브라우저 speaking→idle은 확인했으나, 생성 음성을 다시 전사한 결과에는 단어 오류가 있었다. 전사와 합성 중 어느 쪽에서 생긴 오류인지는 확정하지 않았다. 텍스트 대조는 허용되지 않은 지시를 차단하는 근거이며 발음 품질 인증은 아니다. 사람이 실제로 듣는 검사와 실물 마이크 검사를 따로 남긴다.

## 2026-10-08 기본 통화에서 확인한 함정

- Next의 바인드 URL이 0.0.0.0일 때 브라우저 Origin은 localhost일 수 있다. 실제 Host와 요청 스킴으로 비교하도록 수정하고 회귀 검사했다. 공개 프록시 배포의 출처 설정을 검증한 것은 아니다.
- SDP 응답을 JSON으로 바꾼 개발 중 HMR이 이전 제어기를 유지했다. 전체 페이지 재로드 후 새 런타임으로 검증했다. 전송 계약 변경 후에는 기존 연결을 종료하고 새 페이지로 확인한다.
- 출력 토큰 500 상한에서 불완전 응답을 관찰했다. 1600 상한과 약 60자 존댓말 지침으로 수정하고 completed 응답을 확인했다. 모든 응답 길이를 보장한 것은 아니다.
- 지속 지침에 첫인사를 넣으면 사진을 보낼 때 인사를 반복했다. 첫인사는 session.created 뒤 단발 response.create 지침으로 옮기고 사진 응답을 다시 확인했다.
- 데스크톱 합성 마이크·카메라의 성공과 실제 휴대폰/청취 성공을 구분한다. 최신 실행 근거는 verification.md에 있다.
